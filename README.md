# Codebase Q&A Service

AI-powered codebase Q&A service using GitHub Copilot SDK. Team members authenticate with GitHub and use their own Copilot license to ask questions about codebases.

## Architecture

```
Team Members → GitHub OAuth → Backend (Copilot SDK) → AI Agents → Answers
```

### Features

- 🔐 **GitHub OAuth** - Each user uses their own Copilot license
- 🤖 **3 AI Agents** - Explorer, Analyzer, Architect (specialized for different tasks)
- 💬 **Real-time Streaming** - Live agent activity and responses
- 📚 **Multi-Repository** - Support for multiple codebases
- 🐳 **Docker Deploy** - Easy local deployment
- 💾 **Session Persistence** - Maintains context across questions

## Prerequisites

1. **GitHub Copilot License** - Each team member needs active Copilot subscription
2. **GitHub OAuth App** - For authentication
3. **Docker & Docker Compose** - For running the service

## Setup

### Step 1: Create GitHub OAuth App

1. Go to: https://github.com/settings/developers
2. Click "New OAuth App"
3. Fill in:
   - **Application name**: `Codebase Q&A Service`
   - **Homepage URL**: `http://localhost:3000`
   - **Authorization callback URL**: `http://localhost:3000/api/auth/callback`
4. Click "Register application"
5. Generate a new client secret
6. Save your **Client ID** and **Client Secret**

### Step 2: Configure Environment

```bash
# Copy example env file
cp .env.example .env

# Edit .env and add your GitHub OAuth credentials
# GITHUB_CLIENT_ID=your_client_id_here
# GITHUB_CLIENT_SECRET=your_client_secret_here
# SESSION_SECRET will be auto-generated by setup.sh
```

### Step 3: Add Repositories

```bash
# Clone your team's repositories into the repos/ directory
cd repos
git clone https://github.com/yourorg/project-a
git clone https://github.com/yourorg/project-b
cd ..
```

### Step 4: Build and Run

```bash
# Run setup script (creates .env with random session secret)
chmod +x setup.sh
./setup.sh

# Build Docker containers
docker-compose build

# Start services
docker-compose up -d

# Check logs
docker-compose logs -f
```

### Step 5: Access the Application

Open your browser to: **http://localhost:3000**

## Usage

1. Click "Login with GitHub"
2. Authorize the OAuth app
3. Select a repository from the dropdown
4. Ask questions about the codebase

### Example Questions

- "How does authentication work in this project?"
- "Where is the payment processing logic?"
- "What patterns are used for error handling?"
- "How do I add a new API endpoint?"
- "Find all database queries that don't use transactions"

## AI Agents

The service uses 3 specialized agents that work together:

### 🔍 Code Explorer
- Searches and explores code structure
- Finds files and patterns using grep/glob
- Provides file paths and line numbers

### 🧠 Code Analyzer
- Analyzes code logic and data flow
- Traces execution paths
- Explains patterns and relationships

### 🏗️ Architecture Expert
- Explains high-level system design
- Identifies architectural patterns
- Discusses design decisions

## Troubleshooting

### OAuth callback fails
**Solution:** Verify callback URL in GitHub OAuth app matches: `http://localhost:3000/api/auth/callback`

### No repositories shown
**Solution:** Ensure repositories are cloned into `./repos/` directory

### Copilot SDK errors
**Solution:** Ensure user has active GitHub Copilot license. Check backend logs: `docker-compose logs backend`

### Port already in use
**Solution:** Stop existing services on ports 3000/3001 or modify ports in `docker-compose.yml`

## Cost & Billing

- Uses team members' existing GitHub Copilot licenses
- Each question = 1 premium Copilot request
- Check usage: https://github.com/settings/copilot
- Estimated: 100-500 questions/month per active user

## Security

- OAuth tokens stored in server-side sessions only
- Sessions expire after 24 hours
- Read-only access to repositories (mounted as `:ro`)
- No credentials in logs or client-side code

## Architecture Decisions

### Why GitHub OAuth?
- Each user uses their own Copilot license
- No shared API keys needed
- Proper access control

### Why Docker?
- Easy deployment
- Isolated environment
- Consistent across team

### Why SSE (Server-Sent Events)?
- Real-time streaming responses
- Simpler than WebSockets
- Works with HTTP/2
